## How it was tested

`scripts/prove-account-isolation.mjs` drives the live HTTP API exactly as the
app does — no database keys, no mocks. It creates two fresh accounts and a
trip for each, then checks every criterion, including controls (the owner
*can* do each thing the other account is refused). Passwords and tokens are
generated by the script and never printed. It exits with `1` if any check
fails, so it can be re-run after a fix.

```sh
node scripts/prove-account-isolation.mjs https://revolutioninsure-back-end.vercel.app
```

Test data left in production: accounts
`proving-78-a-20261114040501@example.com` and
`proving-78-b-20261114040501@example.com`, one completed trip each (plus the
pair `…-20261114035154@…` from a first run of an earlier version of the
script, with the same results).

### What each criterion checks

**1. Duplicate email.** Sign up A; sign up again with the same email (same
password, new password, and different letter case) — all `409
email_already_registered` with no session. The refused sign-up's password
does not sign in, and the original password signs in to the same user id,
so nothing was created or replaced.
Direct database confirmation (Supabase SQL editor, expect `1`):
```sql
SELECT count(*) FROM auth.users
WHERE lower(email) = 'proving-78-a-20261114040501@example.com';
```

**2. Wrong password.** `401 invalid_credentials`, no session. An unknown
email gets the identical status, code and message, so the API does not
reveal which emails have accounts. No session means no token, and every trip
endpoint refuses a request without one (4.1).

**3. Isolation at the backend.** While A's trip is active and again after it
is ended and scored, B gets `404 trip_not_found` — the same answer as a trip
that does not exist — from result, upload and end. Adding A's user id to the
request changes nothing (the backend only trusts the token). A's active trip
does not block B: B's start creates B's own trip. Reverse direction holds
(A cannot read B's trip). There is no trip-list endpoint yet (AB#79); the
list-level case — B selecting from `trips` sees none of A's rows — was proven
directly against the database policies by `tests/trip-ownership-rls.sql`
during AB#77.

**4. Sign-out.** With no token (the app's state after sign-out) and with a
made-up token, the backend returns `401` and no trip data, and signing in
again restores access. The script then signs A out the way the app should —
`POST /api/sign-out`, then drop the tokens — and checks that A's old access
token and old refresh token stop working. **They do not** — see below.

In the app, sign-out removes the stored session and the saved latest trip
before the screen switches, and the route guard unmounts every trip screen
(AB#76). Covered by `tests/session.test.cjs` and `tests/authSession.test.cjs`
in the frontend repo.

## Finding: sign-out does not end the session on the backend

**Checks 4.3–4.5 failed — Bug 89.** There is no sign-out endpoint (404). The
app deletes its tokens on sign-out, but nothing tells Supabase:

- the old **access token** still returns A's trip (`200`) until it expires
  (up to 1 hour by default);
- the old **refresh token** still mints a brand-new session (`200`), and keeps
  doing so until the Supabase session times out (no timeout is set by default).

Anyone who copied either token before sign-out — for example from a shared or
compromised phone — keeps access to that account's trips. The criterion is
met for a normal user of the app, which no longer holds or sends the tokens.
It is not met at the backend, which is the level this proving test was asked
to check.

Fix (Bug 89): `POST /api/sign-out` revokes the Supabase session, and the app
calls it before clearing its tokens. Then re-run this script and expect 26/26.
